# ADR-001: 以 P99 稳定性而非最大 CPS 为第一指标

- **状态**：Accepted
- **日期**：2026-07-31
- **决策者**：SteadyChunks 项目

## 上下文

C2ME 等多线程区块生成模组传统上以"每秒区块生成数（CPS）最大化"为主要宣传指标。但玩家在实际跑图过程中体验到的"卡顿"并不与平均 CPS 线性相关：

1. **卡顿来自长尾**：P99 帧时间、P99 MSPT 与超长帧事件比平均帧时间更能预测玩家感知。
2. **完成洪峰**：多线程并行生成完成后，集中回到主线程整合、发送、客户端编译，会形成可观测的尖峰；最大 CPS 路径往往会加剧这种洪峰。
3. **资源争抢**：盲目提高工作线程数会与渲染线程、客户端主线程、GC 争抢 CPU，反而降低玩家可见的流畅度。
4. **冒险整合包特性**：复杂 Jigsaw 结构、大型模板、丰富 FEATURES 的整合包中，长尾远比平均更影响体验。

## 决策

SteadyChunks 的优化目标按以下优先级排序（参见计划 §2.2）：

1. 跑图过程的客户端 P99 帧时间
2. 集成服务器或独立服务器的 P99 MSPT
3. 超过 100 ms / 250 ms / 500 ms 的卡顿事件数量
4. CPU 峰值与渲染线程饥饿
5. FULL 完成、光照和区块发送的洪峰
6. 同时驻留的 ProtoChunk、Future 和生成上下文数量
7. GC 分配率与暂停时间
8. 可见区块从请求到显示的延迟
9. 平均区块生成吞吐量
10. 纯预生成吞吐量

**允许为显著改善 P99 稳定性牺牲少量最大吞吐量**；但不得造成玩家前方长期空洞或明显低于原版的可见区块完成速度。

## 后果

### 正面

- 与玩家真实体验对齐，符合"跑图过程帧时间与 MSPT 稳定性"的项目定位；
- 评估优化时使用 P50/P95/P99/最大值，而非单一平均；
- 允许引入背压、完成整形、发送配额等"反吞吐量"机制。

### 负面

- 必须配套完整诊断模块（Phase 2 Chunk Flight Recorder）才能验证目标达成；
- 在"纯预生成"场景下相对 C2ME 可能不占优甚至略差，需在文档中明确说明项目定位；
- 性能基准需要更长运行时间（多次运行取中位数与置信区间），CI 成本更高。

## 备选方案

### A. 以最大 CPS 为第一指标

被否决：与 C2ME 同质化竞争，且不解决跑图卡顿的核心痛点；需要重新设计才能在 CPS 跑分上超越 C2ME，但即使超越也不代表玩家体验改善。

### B. 以平均帧时间 / 平均 MSPT 为第一指标

被否决：平均值掩盖长尾，无法反映卡顿事件；同一平均值下 P99 可能差异巨大。

### C. 同时优化 P99 与 CPS（不区分优先级）

被否决：当 P99 与 CPS 冲突时无决策依据，会导致实现摇摆。SteadyChunks 选择明确排序，允许在冲突时优先 P99。
